API-Bank → ToolSearcher-Free Benchmark

Conversion of the upstream API-Bank eval data (ToolSearcher removed, all tool definitions inlined in the system prompt) + graded results with Qwen/Qwen3.6-35B-A3B-FP8.

Reference: DAMO-ConvAI/api-bank · HuggingFace split liminghao1630/API-Bank · arXiv:2304.08244

1. What was done

Reproduce the original harness & evaluation data, then convert it to a benchmark that needs no tool-retrieval meta-tool.

  • Smoke-tested the original upstream harness for all three levels (scripts/grade_upstream_original.py) against the proxy — L1 given-desc, L2 toolsearcher, L3 lv3 batch-inference. This confirmed the original data + grading code works and gave a baseline.
  • Harvested a tool catalog from the eight test-data/*.json files: 67 real tools (ToolSearcher excluded), normalised into tool_catalog.json.
  • Rewrote every trajectory (scripts/convert_apibank.py): placed all 67 tool definitions directly in the system prompt and stripped all ToolSearcher calls, return values and spec blobs. Result: level-1 (368 single-turn), level-2 (49 dialogues), level-3 (50 conversations), level-3-batch/-icl (121 per-step rows each).
  • Validated the conversion (scripts/validate_apibank_conversion.py, 1,887 checks) — the processed data differs from upstream only in the ToolSearcher part plus the technical role/format changes. See §4.
  • Graded all levels (scripts/grade_apibank.py, --mode text) with step-replay semantics. Final metrics in §3.

2. How the benchmark changed

The exchange rate is unchanged: same conversations, same gold calls, same gold returns. Only the discovery mechanism (ToolSearcher) is gone; every tool is advertised up-front in the system prompt.

Upstream (original API-Bank)
User: Query meeting of John and send email
      reminder to john@example.com.

[1] ToolSearcher(keywords='QueryMeeting')
    -> {"name":"QueryMeeting", ...}
[2] QueryMeeting(user_name='John')
    -> {"meetings": [...]}
[3] ToolSearcher(keywords='EmailReminder')
    -> {"name":"EmailReminder", ...}
[4] EmailReminder(content='Meeting with the
      client ...', time='...', location='...',
      recipient='john@example.com')
    -> "success"

The model only sees a ToolSearcher spec in the prompt and must retrieve tool definitions at runtime.

ToolSearcher-free (this work)
SYSTEM — all 67 tool specs listed
        (QueryMeeting, EmailReminder, ...)

User: Query meeting of John and send email
      reminder to john@example.com.

[1] QueryMeeting(user_name='John')
    -> {"meetings": [...]}
[2] EmailReminder(content='Meeting with the
      client ...', time='...', location='...',
      recipient='john@example.com')
    -> "success"

ToolSearcher steps and their returns removed; the model picks the right tool directly from the system prompt.

Technical changes (beyond ToolSearcher removal)

  • API (tool) outputs change role: upstream renders API results as system turns; we surface them as OpenAI tool messages (role:"tool", name:<tool>). Qwen3.6's chat template rejects multiple system messages ("System message must be at the beginning"), so this role mapping is required for the target model. Content is identical.
  • System prompt is one fixed block listing every tool in API-Bank's API descriptions format, with an instruction telling the model every tool is already available (no searching).
  • Step-replay grading: after each predicted call, the dialogue advances with the gold call + gold return, so per-step accuracy is independent of earlier model mistakes (matches the upstream eval's per-step oracle-replay semantics).
  • Gold carries gold_tool_calls (ordered calls) + gold_tool_returns (ordered returns) instead of upstream's interleaved ToolSearcher spec strings.
  • 10 unparseable batch rows dropped: level-3-batch gold calls that embed a Python-list literal inside a quoted argument (e.g. attendees='['Mary', 'Peter']') cannot be parsed by the canonical [Tool(...)] parser and were excluded (131 → 121 rows). That is a parsing limitation, not a ToolSearcher difference.

What the validation proves

  • TS-FREE — literally no ToolSearcher string anywhere in the processed benchmark (messages, system prompt, gold calls/returns).
  • GOLD-PRESERVED — for every datapoint, the ordered gold_tool_calls equals the upstream ordered real-tool calls (ToolSearcher dropped, consecutive duplicates collapsed) — for levels 1, 2 and 3 including batch.
  • TEXT-PRESERVED — after removing ToolSearcher artefacts and normalising API-Request: [..]->{..} into (assistant call, tool result) pairs, the user/assistant text stream of each processed conversation is byte-for-byte the same as upstream. The converter deleted retrieval steps but rewrote/invented nothing else.

The system-→-tool role remapping and the fixed all-tools system prompt are declared technical changes and are deliberately not treated as "differences". The only conversion loss is the 10 unparseable level-3-batch rows described in §2.
